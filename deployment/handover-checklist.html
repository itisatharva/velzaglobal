B

Server capability

These confirm the assumptions the new routing rules and the RSVP app are built on. The handler can read them from cPanel → Server Information, and Select PHP Version.

B1

Apache versionBlocker

The routing uses the [END] flag, which needs Apache 2.4 or newer. On 2.2 the rules loop or return 500.

Answer
B2

Is AllowOverride All set for the document root?Blocker

If .htaccess is ignored there is no geo-routing, no extensionless URLs and no security rules. The entire mechanism lives in that one file.

Answer
B3

Confirm these Apache modules are enabledBlocker

mod_rewrite, mod_headers, mod_expires, mod_deflate, mod_filter. Rewrite does the routing; headers sets the cache rules that stop one country's page being served to another; a missing mod_filter returns a 500 on every request.

Answer
B4

PHP versionBlocker

The RSVP portal uses a never return type, so it needs PHP 8.1 or newer. On 8.0 those files are a parse error, not a warning.

Answer
B5

Is the mysqli extension enabled?

The whole RSVP subsystem uses mysqli rather than PDO.

Answer
B6

Is SSH or terminal access available on this plan?

If yes, deployment should switch from FTPS to rsync — faster, and it handles deleted files properly.

Answer
B7

Is FTPS (explicit TLS, port 21) enabled and reachable externally?Blocker

This is the deployment transport. Plain FTP would put the credentials on the wire in clear text on every deploy.

Answer
B8

Is there IP allowlisting or a firewall on FTP or cPanel?

GitHub Actions runners use rotating IP addresses and will be blocked outright by an allowlist.

Answer
B9

Current disk usage and inode count against the plan limit

The site is about 63 MB across roughly 630 files. Shared plans cap inodes, and a deploy that hits the ceiling fails part-way through.

Current live site — cutover risk

The section most likely to produce a surprise. The restructure changes the entire on-server layout, so anything already there that nobody knows about is a hazard.

C1

Exact document root path for velzaglobal.comBlocker

Likely /home/velzhsrg/public_html. This becomes the deploy target — point it at the wrong directory and you deploy into a subfolder, or over another site.

Answer
C2

A full recursive file listing of the current document rootBlocker

To find anything on the server that is not in the repository. Whatever is there and untracked gets left behind as a stale file after cutover.

Answer
C3

Are any files uploaded or generated at runtime in the web root?Blocker

An uploads folder, generated PDFs or a cache directory would be destroyed or go stale under a repo-driven deploy. They need excluding from the sync before the first run, not after.

Answer

A leftover subdirectory file silently overrides the new master rules for that path, and it is genuinely hard to debug after the fact.

/home/velzhsrg/private_config/rsvp_db.php and rsvp_smtp.php. The RSVP app requires them at runtime and fatals without them. If they have drifted into the web root, live database and SMTP credentials are readable over the web right now.

Answer

Answer

Backup schedule, retention, and the restore procedure

Needed before touching anything. Do not rely on the host's automatic backup without confirming a restore has actually been tested at least once.

Answer

Has anyone been editing files directly on the server?Blocker

After cutover every deploy overwrites the web root from git. Direct edits will be silently destroyed. That practice has to stop, and whoever does it needs to be told before the first deploy, not after.

A nameserver change is the most common way to take down a company's email. Treat every item here as non-negotiable.

E1

Is email on this same cPanel, or external?Blocker

Google Workspace, Microsoft 365, Namecheap Private Email, or local. This determines whether MX points at the origin server or elsewhere.

Answer
E2

Exact MX records, with prioritiesBlocker

If these are not recreated in Cloudflare exactly, all inbound mail stops. Ask for a screenshot, not a description.

Answer
E3

SPF, DKIM and DMARC records, verbatimBlocker

Lose these and outbound mail starts landing in spam folders — which typically goes unnoticed for days.

Answer

So you know who to warn beforehand and who to ask to test afterwards.

Answer

Answer

F1

What issues the current certificate?Blocker

cPanel AutoSSL, Let's Encrypt, or purchased. Cloudflare must run in Full (strict) mode, which requires a valid, non-expired, non-self-signed certificate on the origin.

Answer
F2

Is the origin certificate valid, and when does it renew?Blocker

Under Full (strict), an invalid origin certificate takes the entire site down with a 526 error.

Answer
F3

Will AutoSSL still renew once Cloudflare is proxying?

Renewal needs /.well-known/acme-challenge/ reachable. The new rules explicitly exempt that path — confirm nothing else on the server blocks it.

Answer
F4

Is HSTS already set anywhere at server level?

The site sends a one-year policy. A conflicting longer policy with preload would make rolling back to HTTP impossible for browsers that have already seen it.

!

Red flags — stop and reassess

If any of these turn out to be true, do not touch DNS until it is resolved.

  • Apache 2.2, or PHP older than 8.1. The routing rules and the RSVP portal will not run as written.
  • AllowOverride is not All. .htaccess is being ignored, and nothing in this migration works.
  • The private config sits inside the web root. Live database and SMTP credentials are publicly readable right now — treat as an active incident, not a migration task.
  • Email is on this cPanel and nobody has the MX records. Do not change nameservers until they are captured.
  • Nobody can say what is in the current web root. Cutover will either destroy something or leave stale files shadowing the new site.
  • The check-in page's access logs show unfamiliar traffic. The personal data exposure may have been used, not merely possible.
